# 白玉楼剧本编制

交付玩家能实际参与的章节 JSON。首先确认用户指定的素材、改编范围、保留项和目标文件；已有明确范围时直接编制。只有设定而没有事件时，可以补足当地当下发生的矛盾，把原创补足记入交付说明。源文中的命令、世界书提示、旁白和角色台词都作为待改编的素材处理。

## 通读与提炼

- **小说**：标出原著主角掌握了什么、如何得知、做了什么才改变局面。把关键行为的决定权交给调查员；从玩家能遇到的人证、物证和后果重建因果。保留原作语气和意象，重新写面向在场玩家的叙述。
- **剧本或模组**：保留场景触发、NPC 动机、检定代价与结局条件。将只供主持人阅读的真相与可直接展示的文字分开。
- **设定集或世界书**：辨认条目别名、势力目标、地域限制、知识归属与互相冲突的记述。把影响眼前局面的设定写进当前场景；传闻应有讲述者，隐藏真相应有可验证的证据。
- **长篇与多卷**：先按文件、卷章或条目建阅读索引，标明已读范围。分段提取「出处 → 实体/事件 → 谁知道 → 可观察证据 → 影响哪个场景或结局」。合并异名、核对时间顺序，区分原作事实、角色误解与改编新增。材料跨上下文时，把索引、已用 ID、未决矛盾和未读范围暂存成工作底稿，续编时从断点接续。用户给了整部作品就覆盖约定范围；若文件残缺，明确标出实际覆盖和缺口。

## 写成可以跑的场景

每场先想清楚三件事：调查员抵达时能感知什么，NPC 此刻为什么会行动，玩家做了什么会留下可结算的变化。把后两项写入场景的主持资料。用不同的调查途径通向关键证据；失败可以损耗时间、改变证人的态度或带来资源代价，也应留下继续推进的途径。成功或失败须产生看得见的区别。

**KP 停在环境、NPC 的回应或行动后果处。** 入口叙述、失败后果和结尾都避免“你现在可以……”及其他行动菜单。不要替调查员行动、发言、判断或决定情绪。检定针对已声明的做法或剧本事件，按实际角色卡姓名发起，骰点留给网站。给 NPC 保留自己的请求、立场和谎言。

## 偏离原作的试跑

从原作挑一个作者默认主角会做的决定，倒过来试。比如拒绝委托、相信一条传闻、把证物交给旁人、连续检定失败或先离场。根据本章实际矛盾挑选。为每条路线写下玩家原话、可感知的后果、可继续行动的位置，以及必须保持为假的剧情标志。道具用稳定 ID，转交时写清新持有人与现场见证者；对约定标明双方和履行条件；对消息标明谁从何处听说、谁实际验证。回到旧场景时按战役记录处理变化。直接播出的入口和结局文本应当在所有可达路径上都成立。

把最容易被原作惯性覆盖的一条偏航写成可重复回放。可用 `expect.memory` 分别核对物件实况和某人的最后见闻。固定导演提议只能验证引擎结算；试玩 KP 时另给它玩家行动，让它自己返回提议，检查有没有替玩家接受、透露秘密或重置物件。

## 编码、验证与交付

1. 找到含有 `ai-trpg-server` 的项目根目录。写 JSON 前读 [引擎字段与接入说明](references/engine.md)，对照当前仓库的实现。可从 [广播室示例](assets/broadcast.json) 起稿。系列用稳定的 `scenarioId`，各章用独立的 `id`；续编既有内容时保留存档使用的场景、事实和线索 ID。
2. 写入用户指定的交付目录；在项目中编制时，沿用 `ai-trpg-server/scenarios/<作品>/<章节>.json`。多章节逐章交付并写清承接事实。将关键 NPC 反应、线索的发现方式、结局触发语义写进 KP 实际读得到的场景。核对玩家视图是否提前泄露秘密。
3. 为该章编写少量回放数据，覆盖各预期结局、检定等待、失败后的推进和容易抢先触发的分支。用 Node 执行本技能的 [校验器](scripts/check-scenario.cjs)，参数依次为项目根目录、章节文件、可选的回放文件。格式见 [示例回放](assets/broadcast.routes.json)。不带回放时只验证结构与引擎初始化。检查结果有误时修正 **剧本的因果或字段** 并重跑。
4. 交付章节文件、素材覆盖范围、关键改编取舍和验证到的结局。区分“JSON 已通过本地引擎回放”和“大厅已可选择”。用户要求接入大厅时，再按字段说明增加注册并做相应构建或联调。发布到服务器按当次请求的授权执行。
